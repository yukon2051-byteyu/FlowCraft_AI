# FlowCraft AI：面接・ポートフォリオ用のまとめ

面接で「何を・なぜ・どう作ったか」を説明するための資料です。**実測した値と想定の値**、**開発者本人の判断と生成AIが作った部分**を分けて書きます（2026-11-17 時点）。

## 1. 30秒で説明する

> Excelの定型業務を、いきなり自動化するのではなく、まず「その作業は本当に必要か」を見直してから自動化するWebアプリです。
> AIが業務の背景を質問し、廃止→簡素化→標準化→自動化の順に改善を提案します。採用するかは人が決め、採用した改善を処理手順に反映します。
> 処理の結果は、業務の「完了基準」（合計の一致・件数など）で自動的に判定し、問題があれば出力を止めます。
> 生成AI（Claude Code）を使って開発し、私は課題設定・仕様・設計判断・受け入れ確認を担当しました。

## 2. 背景にある業務課題

- 不要な作業まで自動化してしまう（自動化そのものが目的になる）
- 毎月のExcel集計・照合が属人化し、手順が担当者の頭の中にある
- VLOOKUP などの結合で照合漏れ・重複に気づかず、誤った数値を報告してしまう
- 生成AIの答えが正しいか、利用者が判断できない

※ ご自身の業務経験（ヒアリング・要件定義・システム導入）で見た具体的な場面を、ここに一言添えると説得力が増します（誇張せず、実際に見たことだけ）。

## 3. 要件の整理（実装前に決めたこと）

| 項目 | 内容 |
|---|---|
| 目的 | 定型業務のムダをなくし、残す作業は正しく自動化する |
| 利用者 | Excel業務の担当者（プログラミングや専門用語に詳しくない） |
| 入力 | Excel・CSV、業務の説明（任意）、AIの質問への回答（任意） |
| 出力 | 改善提案と判断の記録、処理結果のExcel、品質の判定 |
| 完了条件の例 | AIの提案は利用者の確認なしに確定しない／重大な品質問題があれば正式な出力を止める／AIが使えなくても、AIなしで手順を作れる |

## 4. 技術的な工夫（なぜそうしたか）

| 工夫 | 理由 |
|---|---|
| AIの根拠を「データで確認」「あなたの回答」「AIの推測」に分け、データの根拠はサーバーで材料と照らし合わせる（確かめられなければ推測として表示） | AIはもっともらしい誤り（存在しない列名など）を書くことがある。利用者が根拠の確かさを見分けられるようにするため |
| AIが挙げた「手順に使える部品」を実在する一覧と照らし合わせ、ないものを取り除く。処理ステップは自動で組み立てない | AIの答えをそのまま処理に使うと、動かない手順や誤った処理ができるため。最後は人が確かめる |
| AIに送る文章をサーバーで組み立て、送る前に画面にそのまま見せる。個人情報と思われる列の値は送らない | 何が外部に送られるかを利用者が確かめられるようにするため（情報管理） |
| AI使用パスワード・月の費用上限・回数制限・同じ材料なら再利用 | 公開環境で第三者に使われて費用が膨らむのを防ぐため |
| 判断と理由を作業手順のファイルに残し、次の診断で同じ質問をしない（AIへの指示に加え、サーバーでも重複を取り除く） | 利用者に同じことを何度も聞かないため。AIへの指示は必ず守られるとは限らないので、仕組みで保証する |
| 処理エンジンを自作し、自動の型推定を使わない | 「00123→123」のような黙った変換を避け、結合・集計の検証を1行単位で説明できるようにするため |
| 業務の完了基準で結果を判定し、未設定の重大な基準があれば実行を止める（注意・記録のみは「未検証」として実行） | 「処理が終わった」と「業務として正しい」は別のため |

## 5. 直面した課題と対応（実際に起きたこと）

| 起きたこと | 原因 | 対応 |
|---|---|---|
| 10万行のExcelの読み取りが14〜18秒かかり、目標（10秒）に届かない | 使っていたライブラリの読み取りが遅い | 別のライブラリ（calamine）を比較し、値が同じことをテストで確かめてから切り替え。2.7秒に短縮（実測） |
| 起動し直したのに、AIの設定が反映されない | Windows で古いサーバーのプロセスが残り、新旧2つが同じポートで待ち受けていた | 原因を調べて記録し、起動前に古いプロセスを見つけて確認のうえ止める起動用スクリプトを作成 |
| テスト用のサーバーが、実際のAIの設定（APIキー）を読んでいた | テスト用のサーバーも同じ設定ファイルを読む構成だった | テストでは環境変数で必ずAIを使わない設定に固定し、それが設定ファイルより優先されることを確かめた |
| 診断の記録の日付が1日ずれる | 日時を世界標準時で保存し、日付として先頭10文字を使っていた | 画面写真で発見。利用者のパソコンの時刻と時差で保存するよう修正し、3つの時差でテスト |
| パスワード作成で、空のパスワードを作れた | 長さを確かめていなかった | 実際に使う前のコード確認で発見。8文字未満は作らないよう修正 |

## 6. 数値（実測と想定を分ける）

| 数値 | 区分 | 内容 |
|---|---|---|
| 10万行の処理全体 3.7〜5.5秒、Excelの読み取り 2.7秒 | **実測** | 開発用PCで測定（[performance.md](performance.md)）。ほかの処理と並行したため数秒の揺れあり |
| AI業務改善診断：提案が出るまで30秒以内 | **実測（目安）** | 架空の業務で、開発者本人が実際のAIで1回確認 |
| テスト：サーバー623件・画面の部品201件・E2E 108件 | **実測** | 2026-11-17 時点の件数 |
| 診断1回あたり約10〜15円 | **想定** | AIの料金表と送る文字数からの見積もり。請求額での確認はしていない |
| 業務の作業時間の削減 | **未測定** | 実際の業務での効果は測っていない。デモの「毎月90分」は架空のシナリオの値 |

## 7. 役割分担（誇張しないために）

| 開発者本人が行ったこと | 生成AI（Claude Code）が行ったこと |
|---|---|
| 業務課題と製品方針の設定（「自動化する前に見直す」） | コード・テスト・設計資料の作成 |
| 画面仕様の指示（主要な操作は1つ、AIの質問は増やしすぎない、など） | 選択肢と推奨案の提示 |
| 設計上の判断（AI診断への一本化、未設定の完了基準の扱い、実際のAIは自分で設定して確かめる、など） | テストの実行と結果の報告、不具合の原因調査 |
| 実際のAIでの受け入れ確認、APIキーの管理 | |

面接での表現の例：
- 避ける：「AIアプリを一人で開発しました」（コードの大部分は生成AIが書いているため）
- 使う：「生成AIを開発の相棒にして、課題設定・仕様・設計判断・受け入れ確認を担当しました。AIが書いたコードは、テストと画面での確認で受け入れました」

## 8. 想定される質問と答えの要点

| 質問 | 答えの要点 |
|---|---|
| なぜ自動化の前に見直すのか | 不要な作業を自動化すると、ムダが速く・固定化されるだけだから。業務改善の順番（廃止→簡素化→標準化→自動化）に沿わせた |
| AIの誤りにどう対処したか | 根拠を3種類に分けて示し、データの根拠と手順の部品はサーバーで照らし合わせる。採用は人が決め、処理は自動で組み立てない |
| 情報漏えい・費用の対策は | 送る前に内容を表示、個人情報と思われる値は送らない、パスワード・費用の上限・回数制限。APIキーは設定ファイルに置き、公開しない |
| 品質をどう担保したか | 3段階のテスト（サーバー・画面の部品・実際のブラウザ操作）。正常な操作だけでなく、入力の誤りやAIが使えないときも確かめた |
| 今後の課題は | 業務での効果の実測、AIの提案の質の評価、E2Eテストの安定化、公開環境での確認 |
| 生成AIを使って何を学んだか | AIに任せる部分と人が判断する部分を分けること。AIの答え（コードも提案も）を、テストと仕組みで確かめる習慣 |
