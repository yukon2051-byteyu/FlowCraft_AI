# 品質MVP 設計書（quality-mvp-design.md）

前回実行との比較・品質ルールの再利用・品質検証の履歴を、**手動実行・クラウドWorker・Windows Worker で共通に使える基盤**として作る。
指示書「品質検証機能の強化・MVP追加開発」（2026-11-13）と、確認事項 D-1〜D-7 への回答（同日）による。

## 0. 結論

| 項目 | 決めたこと |
|---|---|
| 品質ルール | 新しい仕組みは作らない。**完了基準（11種類）を品質ルールとして使う**。ルールごとに `rule_id`・`rule_version`・複製元（`origin`）を持たせる |
| 共通基盤（サーバーの Python） | 実行の記録（履歴1件）の形、記録を作る関数、前回の選び方と比較、正式出力の可否の判定を **`app/quality/` に1か所** にまとめる。画面からの実行も Worker も、この関数だけを使う |
| 履歴の保存先 | 手動実行：**ブラウザの IndexedDB**（参考の記録。改変できるため、正式な監査証跡・無人実行の安全判定には使わない）。無人実行：**Worker のデータベース**（Windows は SQLite、クラウドは PostgreSQL（Neon））。記録の形は同じ |
| 前回比較 | **業務の数値**と**品質異常の件数**で、比べる相手の選び方を分ける（§4） |
| 12種類目の基準「前回からの変化」 | 初期は**数値を示すだけ（判定しない）**。閾値を設定したときだけ判定し、初期の重大度は「注意」 |
| デモ | 前月の架空データを実際に処理して比較用の記録を作る。**デモ専用の記録の置き場**に入れ、通常の履歴と混ぜない |

## 2. 実行の記録（履歴1件）の形

`app/quality/record.py` の `RunRecord`（Pydantic）。版を持つ（`record_version: 1`）。**業務データそのものは入れない**（根拠の該当行の例は、完了基準の結果に含まれる最大5件だけ）。

| 区分 | 項目 |
|---|---|
| 識別 | `run_id`・`flow_id`・`flow_name`・`flow_version`・`executed_at`（UTC）・`duration_ms`・`source`（manual／worker／demo） |
| 対象期間 | `period`（実行時に指定する値の月・期間から。なければ空） |
| 入力（3-3） | 入力ごとに `filename`・`sheet`・`sha256`（読み込み時に計算）・`rows`・承認した列の対応付け |
| 処理 | `processing_status`（完了／失敗）・ステップ数・出力する表ごとの件数と指紋 |
| 品質ルール | ルールごとに `rule_id`・`rule_version`・`origin`・**設定の写し**（その時点の基準の JSON） |
| 判定 | ルールごとの判定・重大度・異常件数・根拠（要の値・該当行の例）・総合判定 |
| 指標 | 比較に使う数値（§4）と、その**定義の指紋** |
| 正式出力 | 出力の可否（allowed／needs_confirmation／report_only）・実施したか・停止の理由 |

**過去の記録は書き換えない**：ルールの写しを記録に入れるため、あとでルールや作業手順を変えても、過去の記録の意味は変わらない。

## 3. 品質ルールの版と複製

- 完了基準の各項目に `rule_id`（UUID）と `rule_version`（変更のたびに +1）を足す。作業手順の形の決まりは **1.2** にし、1.1 のファイルは読み込み時に補う（`rule_version: 1`、`rule_id` は新しく作る）
- 複製すると、新しい `rule_id` を作り、`origin: {rule_id, rule_version}` に複製元を記録する。**複製先は複製元の写しで、つながりは記録だけ**（複製元を変えても複製先は変わらない）
- 品質ルール集（ブラウザ）：保存したルールの一覧。別の作業手順に追加するときは、**対象の列を選び直す**。列が見つからないルールは追加できず、確認を求める。実行時に対象の列がない重大なルールは「未検証」になり、正式な出力は止まる（今の総合判定の規則のまま）

## 4. 前回比較

### 4-1. 比べる相手（D-2）

| 比べるもの | 相手 | 見つからないとき |
|---|---|---|
| **業務の数値**（入力件数・出力件数・集計金額） | 同じ作業手順の、**直前の対象期間**の、**正式な出力を行った**記録（複数あれば最新） | 「比較できる前月の正式な出力の記録がありません」。**前々月には飛ばさない** |
| **品質異常の件数**（異常件数・重大件数・照合漏れ・重複） | 同じ作業手順の、直前の対象期間の、**検証まで終わった**記録（正式な出力が止まった回も含む） | 「比較できる前月の検証の記録がありません」 |

- 同じ対象期間（例：11月分を何度もテストした記録）は、前回にしない
- 対象期間が分からない実行（実行時に指定する値がない）は、比較しない（理由を表示）

### 4-2. 比較できない条件

処理の手順が変わっただけでは止めない。**その数値の定義が変わったとき**だけ比較しない。

- 指標ごとに「定義の指紋」を作る：指標の設定（どの表・どの列）＋ その表を作るまでのステップ（上流だけ）の設定
- 指紋が前回と違えば「前回から集計条件が変更されたため、比較できません」。関係のないステップの変更（下流の並べ替えなど）では止めない

### 4-3. 12種類目の基準「前回からの変化」（D-3）

- 対象：指標（件数・合計・異常件数）。初期は **数値を示すだけ**（判定は「記録」）
- 閾値（例：30%以上の減少、前回より増加）を設定したときだけ判定し、超えたら「変化を検出」。重大度の初期値は「注意」（利用者が変えられる）
- 前回の値が 0 のときは増減率を出さず、件数の差だけを示す

## 5. 履歴の保存（D-1）

| 実行のしかた | 保存先 | 位置づけ |
|---|---|---|
| 画面から（手動） | ブラウザの IndexedDB | **参考の記録**。比較と振り返りに使う。正式な監査証跡・無人実行の判定には使わない（画面にも明記） |
| 無人実行（Windows Worker） | SQLite（`scheduled-run-design.md` §5 の `job_runs` に記録を持たせる） | 正式な記録 |
| 無人実行（クラウド） | PostgreSQL（Neon） | 正式な記録 |
| デモ | IndexedDB のデモ専用の置き場（デモを始めるたびに入れ替える） | 通常の履歴と混ぜない（D-5） |

**ブラウザの履歴の扱い**
- 容量：1件はおよそ 5〜30KB。**作業手順ごとに最新200件まで**（古いものから消し、消したことを画面に出す）。ブラウザの保存の上限より十分に小さい
- 消えることがある：ブラウザのデータ削除・プライベートブラウズでは消える。保存の永続化（`navigator.storage.persist()`）を求め、できなかったときは画面で知らせる
- 削除：1件ずつ・作業手順ごと・すべて。いずれも確認してから消す
- 書き出し・取り込み：JSON ファイル（記録の版つき）。取り込むときは形を確かめ、同じ `run_id` は取り込まない。取り込んだ記録には「取り込んだ記録」と表示する

**サーバーは手動実行の履歴を保存しない**（公開版はログインのない共用サーバーのため、他人の業務データが混ざる危険を避ける）。実行の API が記録を返し、画面がブラウザに保存する。前回比較のときは、画面が前回の記録（数値と件数だけ）をサーバーに送り、サーバーの共通関数で比べる。

## 6. 正式出力（変更しない規則の確認）

正常：出力できる／注意・未検証：確認してから（無人実行では案件の設定に従う。初期値は確認待ち）／重大：調査用の確認結果だけ。判定はサーバーの共通関数で行い、画面だけでは決めない。無人実行での上書きの防止は `scheduled-run-design.md` §9 のとおり。

## 7. 作る順番（D-6 の再検討）

無人実行（S1）が使うのは、**記録の形・記録を作る関数・前回の選び方と比較の関数・正式出力の判定**（＝共通基盤）。画面（履歴の一覧・比較の表示・ルール集）は S1 のあとでも手戻りがない。

| 段階 | 内容 | S1 に必要か |
|---|---|---|
| **QM-1 共通基盤** | `RunRecord`・入力の SHA-256 と件数の内訳（3-3）・ルールの版と複製元（形の決まり 1.2）・記録を作る関数・正式出力の判定の関数・実行 API が記録を返す | 必要 |
| **QM-2 前回比較の判定** | 相手の選び方（§4-1）・定義の指紋（§4-2）・12種類目の基準・比較の関数（記録の一覧を受け取って比べる。保存先には依存しない） | 必要 |
| Phase Q | 空白データの規則（設計済み） | 必要（未定義なら無人実行で止める） |
| **S1** | 無人実行の基盤（QM-1・2 と Phase Q を使う。履歴は SQLite） | — |
| **QM-3 画面** | ブラウザの履歴（IndexedDB）・一覧と詳細・結果の画面の前回比較・Excel「確認結果」への追加 | 不要 |
| **QM-4 ルール集** | 品質ルールの一覧・複製・別の作業手順への追加・列の選び直し | 不要 |
| **QM-5 デモと TOP** | デモへの組み込み（前月の記録・ルールの複製・履歴）・TOP の「開発中」を外し、各画面への導線をつける | 不要 |

## 8. テスト（指示書 §15 との対応）

QM-1・2 は Python の単体テストで、前回比較の8ケース（正常・前月なし・前月0・同じ月の再実行・定義の変更・大幅減少・異常件数の増加・不適切な履歴）と、記録の不変性（ルール・作業手順の変更後も過去の記録が変わらない）、別の実行IDを確かめる。二重実行の防止と上書きの防止は S1 のテストで確かめる。画面の操作は QM-3〜5 の E2E で確かめる。

## 9. 作らないもの

組織横断のルール配布・権限管理・監査証跡システム・AI によるルールの変更や承認・統計的な異常検知（指示書 §17）。**品質基準の変更は、必ず利用者が確認して行う。**
