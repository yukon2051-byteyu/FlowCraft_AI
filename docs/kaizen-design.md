## 1. 位置付け

> **不要な作業を、わざわざ自動化しない。**

改善の検討順序は **廃止 → 簡素化 → 標準化 → 自動化**。すべての業務を廃止から始めるという意味ではなく、自動化の前に「なくせないか・減らせないか・そろえられないか」を一度確かめる、という原則。

**範囲**：Excel・CSV を使う業務に限る。業務全般の課題の聞き取り・原因分析・実行計画は AI-BIC（別アプリ）の役割とし、FlowCraft AI では扱わない。

**FlowCraft AI ならではの点**：改善案を**実際の作業手順の変更 → テスト実行 → 完了基準での確認 → 効果の測定**までつなげること。改善の助言だけなら、汎用の生成AIや AI-BIC でもできる（§9）。

**強制しない**：簡単な加工・集計をしたいだけの利用者には、カイゼン支援を見せても押し付けない。作業手順の画面の横に「見直す」の入口を置き、開いたときだけ使う。

## 2. 3つの部品

| # | 部品 | 中身 | AI | MVP |
|---|---|---|---|---|
| A | **目的のメモと簡易チェック** | 作業の目的・使う人・使い道・実施しないと困ることを、作業手順と一緒に記録。6問の はい／いいえ／分からない で改善の方向を示す | 使わない（後で、質問を絞り込む用途に使う） | ○ |
| B | **作業手順の分析** | 保存・作成済みの作業手順を、決まった規則で調べ、改善の候補を根拠つきで示す | 使わない | ○ |
| C | **改善の反映と効果の測定** | 選んだ改善案を作業手順の変更案にし、変更前と変更後を同じデータで実行して比べる。完了基準を満たさなくなる改善は採用させない | 使わない（後で、変更案の作成をAIが手伝う） | 次の段階 |

**AIを後回しにする理由**：B・C は規則とプログラムで決定的に行える。同じ手順なら同じ指摘になり、理由も説明できる。AI はその上に「質問の絞り込み」「説明の言い換え」「規則にない改善の候補」として足す（Phase 5）。AIの推測だけで「作業が不要」と断定しない。

## 3. A：目的のメモと簡易チェック

### 3.1 目的のメモ（すべて任意）

| 項目 | 例 |
|---|---|
| この作業の目的 | 部署別の売上を、月初の営業会議で確認するため |
| 成果物を使う人 | 営業部長、各部署のリーダー |
| 何の判断に使うか | 翌月の重点商品の決定 |
| 実施しなかった場合に困ること | 会議で部署別の実績が分からない |

作業手順のファイルに保存する。**引き継ぎのとき、手順だけでなく「なぜこの作業をしているか」が残る**ことに独立した価値がある。

### 3.2 簡易チェック（6問・いつでも途中でやめられる）

| # | 質問 | 「はい」のときに示す方向 |
|---|---|---|
| 1 | 同じ情報を、別のシステムや既存の帳票で確認できますか？ | 廃止を検討（**要確認**：目的が本当に同じか、監査・規程上の必要がないか） |
| 2 | 成果物の中に、最近使われていない集計や列がありますか？ | 簡素化を検討 |
| 3 | 同じ情報を、2回以上入力・転記していますか？ | 簡素化を検討 |
| 4 | 担当者や部署によって、Excelの形式・列名・集計方法が違いますか？ | 標準化を検討 |
| 5 | 手入力やコピー＆ペーストがありますか？ | 自動化・ポカヨケ（入力の誤りを起こしにくくする工夫）を検討 |
| 6 | 毎回、同じ確認や手直しをしていますか？ | 自動化（完了基準として登録）を検討 |

- 「分からない」が多いときは「**追加確認が必要**」と表示する。
- 方向は決まった対応表で示す（AIの推測ではない）。表示は「検討してください」までで、「不要です」とは言わない。
- 法令・監査・内部統制・契約・社内規程で必要な作業がある旨を、廃止の方向を示すときに必ず添える。

## 4. B：作業手順の分析（決まった規則）

| 規則 | 見つけるもの | 改善案 | 方向 | 効果の示し方 |
|---|---|---|---|---|
| K1 | 読み込んだ直後に、列を消す・取り出すステップがある | 読み込む列を減らし、ステップをなくす | 簡素化 | ステップ数 −1（確実） |
| K2 | 同じ表に対する、連続した「条件に合う行だけ残す」 | 1つのステップにまとめる | 簡素化 | ステップ数（確実） |
| K3 | 連続した「列の名前を変える／必要な列を取り出す／不要な列を消す」 | 1つにまとめる | 簡素化 | ステップ数（確実） |
| K4 | どこにも使われず、出力もされない結果（作業手順の検証 R4 で検出済み） | ステップを削除 | 廃止 | ステップ数（確実） |
| K5 | 作ったが、出力にも後の処理にも使われない列 | 作らない | 簡素化 | 列数（確実） |
| K6 | 集計の直前の並べ替え（集計結果は項目の順に並ぶため意味がない） | 並べ替えを削除 | 廃止 | ステップ数（確実） |
| K7 | 毎回の実行で「データの形式をそろえる」「空欄を埋める」「前後の空白を取り除く」が必要になっている | 提出してもらうExcelの形式を統一する（アプリの外の改善）。入力側のポカヨケ（選択式・必須チェック）を提案 | 標準化 | 実行記録の件数（Phase 6 以降。履歴が少ないときは「推測」と明示） |
| K8 | 毎回同じ警告（照合できない商品コードなど） | マスタの管理方法を見直す | 標準化 | 警告の件数（実測） |
| K9 | 時間のかかるステップ | 処理の順番の入れ替え（行を先に絞るなど） | 簡素化 | 実行時間（実測） |

**各提案の表示**（指示書 §5.3）：改善対象の工程／問題と考えられる理由／改善案／期待できる効果（実測・確実・推測の区別つき）／実施上の注意点／確認が必要なこと。「効率化できます」だけの表示はしない。

規則は作業手順の構造（参照名・列）から計算するため、既存の `ops.ts`（1-3 の「この結果を使うステップ」など）とサーバーの作業手順の検証（R4 など）をそのまま使える。

## 5. C：改善の反映・比較・効果の測定

### 5.1 流れ

1. 改善案を選ぶ（複数可）
2. **元の作業手順を残したまま**、変更案（複製）を作る
3. 変更前と変更後の違いを表示（追加・削除・変更したステップ）
4. 同じ入力ファイルで、変更前と変更後をテスト実行
5. 比べる：出力の一致（既存の「表の指紋」で判定）、件数、実行時間、警告の数、完了基準の総合判定
6. 採用するかを利用者が決める。**AIや規則が自動で採用することはない**
7. 採用したら、改善の記録（理由・選んだ案・変更前後の測定値・日時）を作業手順に残す

### 5.2 判定

| 状況 | 表示 |
|---|---|
| 出力が一致し、完了基準の判定が悪くならない | 「結果は変わらず、ステップが3つ減りました（実測）」 |
| 出力が変わる（業務の目的を変える改善） | 一致を求めず、新しい完了基準で評価する。変わった件数・列を表示 |
| 完了基準の判定が悪くなる | **改善として採用できない**。処理時間が短くなっても同じ |

### 5.3 効果の測定

| 区分 | 項目 | 出どころ |
|---|---|---|
| 実測 | 実行時間、ステップ数、入力・出力の件数、警告・エラーの件数、総合判定 | アプリが測る |
| 利用者の入力 | 従来の手作業の時間（1回あたり）、月の実施回数、担当人数 | 利用者が入力（任意） |
| 試算 | 削減時間 ＝（従来の時間 − 改善後の時間）× 回数 | **「入力値にもとづく試算」と表示** |

例：従来 1回4時間・改善後 10分・月1回 → 1回あたり3時間50分、年間 約46時間の削減（試算）。

人件費への換算は MVP では行わない（単価の根拠がなく、根拠のない金額が独り歩きしやすいため）。

## 6. 改善案の比較（指示書 §6）

複数の方向がある場合、次の表で並べる。**数値は実測か利用者の入力がある項目だけに入れ、なければ空欄（「未測定」）にする**。AIが数値を作ることはしない。

| 比較項目 | 案A 現在の作業を自動化 | 案B 簡素化してから自動化 | 案C 作業の廃止を検討 |
|---|---|---|---|
| 効果 | 実測（テスト実行） | 実測（テスト実行） | 未測定（業務側で確認） |
| 実現の難しさ | 低：この画面で完結 | 中：手順の変更 | 高：関係者との調整 |
| リスク | 不要な作業が残る | 成果物の形が変わる場合あり | 使っている部署・内部統制への影響 |
| 必要な調整 | なし | 成果物を使う人への確認 | 利用部署・管理部門 |

## 7. 単発業務と定型業務

| | 単発業務 | 定型業務 |
|---|---|---|
| A 目的のメモ・簡易チェック | 任意（入口を表示するだけ） | 保存時に入力を勧める（任意） |
| B 作業手順の分析 | 作った手順に対して、いつでも | 保存した手順に対して。実行記録があれば K7〜K9 を実測で |
| C 反映・効果 | テスト実行の比較まで | 採用の記録を残し、翌月以降の実行で効果を確かめる |
| 実行記録が少ない | — | 「記録が◯回分のため、推測を含みます」と明示 |

## 8. データの形（作業手順ファイル 1.1 に含める）

完了基準と同じ 1.1 で、次の任意項目を追加する（1回の版上げで済ませる）。

```jsonc
"purpose": { "goal": "…", "users": "…", "decision": "…", "if_not_done": "…" },
"kaizen_check": { "answers": { "q1": "yes", "q2": "unknown" }, "answered_at": "…" },
"improvement_log": [
  { "applied_at": "…", "rules": ["K1", "K3"], "summary": "読み込む列を絞り、列の整理を1ステップに統合",
    "before": { "steps": 9, "duration_ms": 4200 }, "after": { "steps": 6, "duration_ms": 3100 },
    "outputs_identical": true, "verdict_before": "正常", "verdict_after": "正常" }
]
```

業務データの中身は保存しない（件数・時間・判定・指紋のみ）。

## 9. 生成AIとの差別化として本当に有効な部分

| 部分 | 有効か | 理由 |
|---|---|---|
| 改善案 → 手順の変更 → 同じデータで前後を実行 → 出力の一致と完了基準で確認 → 採用の記録 | **有効** | 生成AIでも各段階はできるが、毎回の指示と結果の突き合わせを利用者が行う必要がある。FlowCraft AI では一連の操作として、根拠の数値つきで残る |
| 決まった規則による手順の分析（K1〜K9） | やや有効 | 生成AIもコードを読めば指摘できる。違いは「頼まなくても出る」「同じ手順なら同じ指摘」「効果がテスト実行で実測される」こと |
| 目的のメモ | 有効（引き継ぎの観点） | 手順と目的が1つのファイルに残る。差別化というより実務上の価値 |
| 業務の必要性を問う質問・なぜを繰り返す深掘り | **弱い** | 汎用の生成AIや AI-BIC で同等以上にできる。FlowCraft AI では6問のチェックにとどめる |
| 効果の金額換算 | 弱い・危険 | 根拠のない数字になりやすい |

## 10. 実装を推奨しない機能

| 機能 | 理由 |
|---|---|
| AIとの対話による長い業務ヒアリング・なぜなぜ分析 | AI-BIC と重複。単純な処理をしたい利用者の妨げになる |
| AIが「この作業は不要」と判定する機能 | 法令・監査・規程による必要性をAIは確認できない。誤った廃止の責任を負えない |
| 人件費の自動換算 | 単価の根拠がない。試算が実測のように扱われやすい |
| 部署間での改善事例の共有 | 利用者管理とサーバー保存が必要。データを残さない方針（公開版）と合わない |
| カイゼン診断のダミー画面（TOP用） | 未実装の機能を使えるように見せることになる（指示書 TOP §7 と同じ判断） |
| 実行記録が1〜2回しかない段階での「継続的な改善提案」 | 根拠が足りず、推測を事実のように見せてしまう |

## 11. 2つのルートと切り替え（追加指示：カイゼン診断は任意）

### 11.1 始め方

| ルート | 内容 | 状況 |
|---|---|---|
| **A. すぐにExcel作業を自動化する** | これまでどおり、ファイルを読み込んで作業手順を作る・実行する | 使える（開始画面で最初から選ばれている） |
| **B. 作業の見直しから始める** | 目的のメモ・簡易チェック → 改善の方向と改善案を確認・選択 → 必要なExcel処理の作成へ進む | 開発中（Phase K1）。開始画面には「開発中」として表示し、選べない。見せかけの画面は作らない |

「今回だけ／繰り返し」（確認事項 V1）とは別の軸である。V1 のとおり、保存するかどうかは最後に選ぶ。

### 11.2 切り替え

| 切り替え | 方法 | 残すもの |
|---|---|---|
| A の途中 → 見直し | 作業手順の画面の「この作業を見直す」（開発中のあいだは押せない） | 読み込んだファイル、使う列と形式、作った処理ステップ |
| B の途中 → 自動化 | 見直しの画面の「自動化に進む」（簡易チェックは途中でやめてよい） | 入力した目的のメモ・チェックの回答（作業手順に保存される） |

**状態の持ち方**（画面の状態管理を複雑にしないため）

- 目的のメモ・チェックの回答は、作業手順そのもの（`purpose`・`kaizen_check`）に持つ。ルートを切り替えても、同じ作業手順の中にあるので失われない
- 改善を反映した手順は、**下書き**（状態管理の `draftFlow`）として作業手順とは別に持つ。利用者が確認して「採用する」を押すまで、作業手順（`flow`）は書き換えない
- 「今どちらのルートにいるか」は画面の表示状態だけで持ち、保存しない

### 11.3 品質の確認は共通

ルート A・B のどちらでも、また見直しを途中でやめても、**標準の確認と完了基準の評価は必ず行う**。見直しを省いたことで確認が省かれることはない（処理エンジンと確認の仕組みは1つ）。

## 12. 配色（UI配色改善指示書：コーラルレッドの導入）

| 色 | トークン | 意味 | カイゼン支援での使い方 |
|---|---|---|---|
| ミント | `mint` | 主役。実行・成功・主要操作 | 改善案を採用した後の実行・正常判定 |
| ゴールド | `warning` | 注意・確認が必要 | 確認が必要な項目 |
| コーラルレッド（#D97772） | `kaizen`（文字は `kaizen-text`、明るい面では `kaizen-ink`／`kaizen-soft`） | 問題提起・ムダの発見・カイゼンのきっかけ | 作業の必要性を問う質問、ムダ・重複工程の発見、改善前の課題 |
| レッド | `error` | エラー・重大 | 使わない |

- 改善案カードは全体を赤くせず、**左側のアクセントライン・アイコン（電球・虫眼鏡）・小さなラベル（「改善候補」「見直しの提案」）**に限る。本文は通常の文字色
- コーラルとエラーの赤は色味が近いため、色だけで区別しない。コーラルには電球・虫眼鏡と「見直し」「ムダ」「改善候補」、エラーには警告・×のアイコンと「重大」「エラー」を必ず添える
- 使う量は少なく（面積の約5%）。2026-11-12 時点の適用箇所は、TOPのヒーロー図「見直す」と「05 作業そのものを改善できる」のカードだけ
- コントラスト（実測）：コーラル／暗いパネル 5.11:1、`kaizen-text`／暗いパネル 6.91:1、`kaizen-ink`／明るいカード 5.80:1（いずれも 4.5:1 以上）
