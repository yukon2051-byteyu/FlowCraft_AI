## 2. 案件ごとの正常／NG（原因を案件ごとに変える）

| 案件 | 正常 | NG（品質異常）とその原因 | 検出する仕組み（実データ・実際の処理で） | 見せる機能 |
|---|---|---|---|---|
| 月次売上集計（既存） | 10月分の伝票だけ | **対象期間外の伝票の混入**（11月の伝票が数件） | 完了基準「対象月の伝票だけ」（重大） | 期間の確認、根拠（期間外の件数・日付）、正式出力の停止 |
| 商品マスタ照合（新規） | すべての商品コードを照合できる | **未登録の商品コードと表記揺れ**（前後の空白・全角） | 完了基準「照合できない行が0件」（重大）＋原因の内訳 | 照合、未照合の件数、原因の候補（空白・全角・未登録）、原因ごとの直し方 |
| 在庫差異検出（既存カード） | 入出庫に問題がない | **伝票番号の重複（二重計上）** | 完了基準「伝票番号が重複しない」（重大）＋「在庫の差異の一覧」（記録） | 重複の検出、二重計上の防止 |
| 勤怠データ集計（新規） | 必要な勤務データがそろっている | **必須項目（出勤・退勤）の空欄** | Phase Q の空白データのルール（未定義なら確認を求める） | 空白の検出、品質ルール、利用者の確認 |

- **NG のデータは「正常のデータに問題を入れたもの」として作る**（シード固定）。問題の行・件数は `manifest.json` に記録し、テストで照合する
- 勤怠データ集計は Phase Q（空白データのルール）を使うため、Phase Q の後に追加する

## 3. 画面の流れ

```text
TOP「デモ」 → 案件を選ぶ → 「正常終了を体験する」／「品質異常の検出を体験する」
  → デモのファイルと作業手順（完了基準つき）を自動で読み込む（サーバーの POST /api/demos/{案件}/start?pattern=ok|ng）
  → いつもの作業手順の画面（中身を見られる・変えられる）→ 実行 → 結果の画面（総合判定・根拠）→ Excel
  NG のとき：結果の画面に「直して再実行する」
  → 修正済みのデータ（＝正常のデータ）で同じ作業手順を実行 → 修正前／修正後を並べて比較
```

- デモ専用の判定・文章は作らない。**判定はすべて実際の処理エンジンと完了基準の評価から出す**（判定の作り込み・架空の実行履歴は禁止）
- 選んだ後の操作は、通常の作業と同じ画面を使う（デモのための別の画面を増やさない）

## 4. 「直し方の案内」と修正前後の比較（補足の提案）

| 表示 | 例（商品マスタ照合） |
|---|---|
| 何が問題か | 照合できない行 9行（重大） |
| 原因ごとの直し方 | 前後の空白 2行：空白を取り除く ／ マスタにない値 4行：マスタに登録 ／ 空欄 3行：値を入力（2026-11-13 に実装済みの原因の内訳を使う） |
| 修正前／修正後の比較 | 総合判定：重大 → 正常、照合できない行：9 → 0、売上合計：21,448,960 → 21,448,960（金額は変わらない）、正式出力：停止 → 出力できる |

比較は、2回の実行結果（判定・完了基準ごとの結果・件数・合計）を並べるだけで作れる（Phase 6「前回の実行との比較」の一部を前倒しする）。

## 5. 3分後の自動実行デモ（cloud-demo-design.md）との関係

- クラウドの3分後デモでも、案件と「正常／NG」を選べるようにする（初めは通常のデモを先に作る）
- NG のとき、Worker が品質異常を見つけて正式出力を止めたことを、実行履歴に残す
