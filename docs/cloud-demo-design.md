- 版：v0.1（2026-11-13 指示書 Phase 1「実行基盤の検証」の結果。実装は未着手）
- 元の指示：クラウド無人実行・3分後の実動作デモ 開発指示書（2026-11-13）
- 前提：[scheduled-run-design.md](scheduled-run-design.md)（共通Worker方式・5段階の確認）。**この設計は、その共通Worker をクラウドでも動かすための追加**であり、別の仕組みを作るものではない
- 料金・無料枠は 2026-11-13 に調べた値。変わることがあるため、契約・設定の前にもう一度確認する

## 0. 結論

| 項目 | 採用案（費用 0円・クレジットカード不要） |
|---|---|
| 実行の合図（スケジューラー） | **Upstash QStash の「遅延メッセージ」**：有効化した時刻＋3分に、Worker の入口（HTTPS）を1回呼ぶ。無料枠 1日1,000通 |
| 予備の合図 | GitHub Actions の定期実行（10分ごと）：合図が届かなかった予約を拾う「見回り」。正確さは求めない |
| Worker | 共通Worker の「実行対象の判定 → 実行権の確保 → 実行」（`run_due_jobs`）を、HTTPS の入口から呼べるようにしたもの。Windows では同じ処理をタスクスケジューラから呼ぶ |
| データベース | **Neon（PostgreSQL）無料プラン**：1プロジェクト 1GB・月100時間分の計算（5分使わないと停止し、次の接続で数秒以内に再開） |
| 結果ファイルの保存 | データベースの中に保存（デモの出力は小さいため。**24時間で自動削除**） |
| Web | Hugging Face Spaces（公開は Phase 9-4。**公開の前に確認をもらう**） |
| 実行の正確さ（見込み） | 予定から**数秒〜十数秒**の遅れ（合図の遅れ＋データベースの再開＋処理）。**実測値は実装後に記録する**。画面では「3分後ちょうどを保証するものではありません」と表示 |

**この案を選んだ理由**：追加費用とカード登録がなく、合図は秒単位で届き、合図を受けた後の判断（実行してよいか・二重でないか）はすべてデータベースで行うため、共通Worker の安全設計（5段階の確認・一意制約による二重実行の防止）をそのまま使える。

## 1. 候補の比較

| 候補 | 実行の正確さ | 無料枠・費用 | 制約・リスク | 評価 |
|---|---|---|---|---|
| A. GitHub Actions の定期実行だけ | ✕ 最短5分間隔。混雑時は遅れ、**実行されないこともある**（公式の注意書き） | 公開リポジトリは無料 | 3分後の実行には使えない | 予備の「見回り」にだけ使う |
| B. **QStash（遅延メッセージ）＋ Worker の入口** | ◎ 秒単位 | 無料：1日1,000通（再送も1通に数える）。超過は10万通あたり1ドル | 外部サービスに1つ依存。合図の受け取りには署名の確認が必要 | **採用** |
| C. Google Cloud（Cloud Tasks ＋ Cloud Run ＋ Cloud Storage） | ◎ 秒単位 | 無料枠の範囲で0円の見込み（Cloud Run：月200万リクエスト等） | **請求先アカウント（カード）の登録が必要**。設定が多く、初心者には保守が重い | 将来、利用者が増えたときの移行先 |
| D. 常時動く Worker（小さな仮想サーバーで15秒ごとに確認） | ○ 15秒以内 | 常時無料の枠はカード登録が必要なものが多い。有料なら月5〜7ドル程度 | サーバーの保守（更新・監視）が必要 | 費用をかけられる段階での候補 |
| E. Spaces の中のタイマー・常駐スレッド | — | — | **指示書で禁止**。Spaces が再起動すると予約が消える | 不採用 |

**データベースの比較**

| 候補 | 評価 |
|---|---|
| SQLite（ファイル） | Web と Worker が別の環境になると共有できない。無料の Spaces はディスクが消える → **クラウドでは不採用**（ローカル版・Windows Worker では引き続き使う） |
| Hugging Face の永続ストレージ | 有料（20GBで月5ドル）。Spaces の外の Worker からは読めない → 不採用 |
| **Neon（PostgreSQL）無料** | カード不要。1GB・月100時間分の計算。自動停止は5分（無料プランでは変更不可）→ **採用** |
| Supabase 無料 | 使われない期間が続くとプロジェクトが一時停止する。Neon で足りるため不採用 |

**結果ファイルの保存先**：デモの出力は数十KBのため、データベースに保存して24時間で消す。別のストレージサービスを増やさない（管理するサービスが少ないほど、初心者でも保守しやすい）。将来、利用者のファイルを扱うときはオブジェクトストレージ（Cloudflare R2 など）に移す。

## 2. 構成と流れ

```text
利用者のブラウザ
   │ ①デモ案件を選ぶ → 5段階の確認 → ②「3分後の自動実行を有効化」
   ▼
FlowCraft AI Web（Hugging Face Spaces・FastAPI）
   │ ③有効化した時刻＋3分を、サーバーの時計で実行予定として保存（UTC）
   │ ④QStash に「3分後にこの入口を呼んで」と依頼（予約のIDだけを渡す）
   ▼
Neon（PostgreSQL）：案件・設定の版・確認結果・実行予定・実行履歴・結果ファイル

   ……ブラウザを閉じてもよい……

QStash（3分後）──→ Worker の入口 POST /api/worker/tick（署名を確認）
GitHub Actions（10分ごと・予備）──→ 同じ入口（専用の合言葉で認証）
   │
   ▼
共通Worker run_due_jobs(今)
   ├ 実行予定 ≦ 今 の「有効」な予約を探す（合図の中身は信用せず、必ずデータベースで判断）
   ├ (予約ID, 実行予定) の一意制約で実行権を確保 → 二重実行しない
   ├ 状態と設定の版を再確認
   ├ デモのサンプルExcelを読み込み → 既存のエンジンで加工・集計 → 品質検証（完了基準）
   ├ 正常なら結果のExcel（既存の app/export）をデータベースに保存
   └ 実行履歴：予定・実際の開始・終了・件数・判定・エラー
   ▼
利用者が再びアクセス → 復元用のリンクで状態と結果を表示 → ダウンロード
```

- **合図は「起こすだけ」**。何を実行するかは、Worker がデータベースを見て決める。合図が2回届いても、見回りと重なっても、一意制約で1回しか実行しない
- **Spaces が止まっていた場合**：予約の直前まで利用者が使っているため、3分後に Spaces が眠っている可能性は低い（無料の CPU は48時間使われないと停止）。それでも合図が失敗したときは、QStash の再送と GitHub Actions の見回りで拾い、**遅れた事実を「実行遅延」として表示する**（成功したように見せない）
- Windows Worker との違いは「誰が起こすか」だけ（Windows：タスクスケジューラが5分ごと／クラウド：QStash が予定の時刻に）。判定・確保・実行・品質検証・記録は同じコード

## 3. 3分後の時刻の決め方

- 基準は**利用者が最終確認画面で有効化した時刻**（設定を始めた時刻ではない）。サーバーの時計で決め、UTC で保存し、画面では日本時間で表示する
- 実行履歴に「予定」「実際の開始」「差（秒）」を記録し、結果の画面に表示する：例「予定 10:03:00 → 開始 10:03:04（4秒後）」
- 待機画面のカウントダウンは表示のためだけ。0になっても画面からは何も実行しない。状態は数秒ごとにサーバーへ問い合わせる

## 4. 他人の結果を見られないようにする（認証なしの公開デモ）

- 予約ごとに、推測できない**復元用の合言葉**（32バイトの乱数）を発行する。データベースには合言葉そのものではなく指紋（ハッシュ）だけを保存する
- 復元用のリンクは `…/demo/schedule#<予約ID>.<合言葉>`。`#` の後ろはサーバーのアクセスログに残らない。同じブラウザでは localStorage にも保存し、ブラウザを閉じて開き直しても続きを表示できる
- 予約・結果・ダウンロードの API はすべて合言葉を確認する。合言葉が違えば「見つかりません」と返す（存在するかどうかも教えない）

## 5. 公開デモの利用制限

| 制限 | 値（初期案） |
|---|---|
| 使えるデータ | **用意したサンプルデータだけ**（利用者のファイル・外部URL・任意のプログラムは受け付けない） |
| 同時に待機できる予約 | 1つのブラウザにつき1件 |
| 1日の実行回数 | 1つのブラウザにつき5回、全体で200回（QStash の無料枠1,000通に余裕を残す） |
| 1回の処理時間の上限 | 60秒（超えたら失敗として記録） |
| 実行履歴・結果ファイルの保存 | 24時間で自動削除 |
| 大量の予約への対策 | 接続元ごとの回数制限、全体の上限に達したら「本日の受付は終了しました」 |

## 6. デモの案件

- 「月次売上集計」：既存のデモと同じ架空データ（売上実績・商品マスタ・部署マスタ）と作業手順（`backend/app/demos/flows/monthly_sales.json`）を使い、**実際に読み込み・照合・集計して** Excel を作る。作っておいたファイルを返すことはしない
- 品質検証は Phase 2 の完了基準（必須列・欠損・重複・件数・合計の照合・対象期間）を使う
- 将来：わざと問題を入れたデータで「品質検証で止まる」デモも選べるようにする（案件を一覧で持つ作り）
- 事前のテスト実行の結果と、3分後の本番の結果は、画面とファイル名で区別する（「テスト実行」「自動実行」）

## 7. 作る時期（提案）

この機能は、無人定期実行の基盤（S1）・完了基準（Phase 2）の上に乗る。順番は次のとおりとする。

1. Phase 1 の残り（1-9〜1-11）→ Phase 2 → Phase 3 → M1
2. **S1 の中で、まずクラウドの3分後デモを完成させ（共通部分を先に固める）、続けて Windows Worker を仕上げる**
3. 公開（9-4）の確認をもらってから、Neon・QStash を本番として設定し、ブラウザを閉じた状態での実行を実際に確かめる

**利用者にお願いすること（その段階で改めて確認する）**：Neon と Upstash のアカウント作成（無料・カード不要）、Hugging Face Spaces への公開の承認、接続情報を Spaces の「Secrets」に登録すること。接続情報はリポジトリに入れない。

## 8. 確かめ方（必須テスト15件への対応）

- 自動テスト：時刻を指定できる Worker で、予約の保存・有効化前は実行しない・二重の合図で1回だけ・Worker の再起動後も履歴が残る・失敗を成功と表示しない・合言葉が違うと見られない・複数の予約の混在、を確かめる
- 実際の動作確認（公開後）：予約 → **ブラウザを閉じる** → 3分以上待つ → 開き直して結果を確認。予定と実際の開始の差を、複数回測って記録する（**実測値として記録し、見込みと区別する**）
