## 1. 基本の考え方

> **処理がエラーなく終わったことと、業務が正しく完了したことは同じではない。**

例：売上の集計がエラーなく終わっても、10月分のファイルに11月の伝票が混ざっていれば、業務としては誤り。処理は正しく動くので、処理の検証だけでは気づけない。

そこで FlowCraft AI は、次の4つを**別のもの**として持つ。

| # | 名前（画面） | 内部名 | 中身 | 誰が決めるか |
|---|---|---|---|---|
| 1 | 何をする？（作業手順） | `nodes` | どの処理を、どの順で行うか | 作る人（AIの提案を確認） |
| 2 | 何を満たせば完了？（完了基準） | `completion_criteria` | 結果が満たすべき条件・期待値・許容範囲・満たさないときの重さ | 作る人（テンプレート・手動・AIの提案を確認） |
| 3 | 確認の結果 | 実行結果の `checks` | 各条件を実際に満たしたか、その根拠の数値 | **プログラムが計算**（AIは使わない） |
| 4 | 総合判定 | 実行結果の `verdict` | 正常／注意／重大／未検証 | **決まった規則で計算**（AIは使わない） |

1・2 は作業手順のファイルに保存する。3・4 は実行のたびに作り、ファイルには「前回の実行の要約」だけを残す（U1）。

## 2. 確認の2つの層

| 層 | 画面の名前 | 中身 | 設定 |
|---|---|---|---|
| 標準の確認 | 標準の確認（自動） | これまでに実装した処理の検証：結合の関係・行数の予測・結合前後の金額・集計前後の合計と件数・データの形式の変換・必要な列 | **不要**。すべての作業で必ず行う |
| 業務の完了基準 | 完了基準 | 業務ごとの条件：対象期間・正解値・照合できない件数の上限・重複なし・値の範囲など | 必要なときだけ追加する |

**設定の負担を増やさない**：簡単な単発業務は「標準の確認」だけで実行できる。
**ただし保証しすぎない**：業務の完了基準が1つもないときは、判定を「正常」と表示せず、

> 標準の確認で問題は見つかりませんでした（業務の完了基準は設定されていません）

と表示する。業務上の正しさまで確かめたように見せない。

## 3. データの形（作業手順ファイル 1.1）

作業手順の形の決まりを 1.0 → **1.1** に上げ、次の項目を追加する。**1.0 のファイルはそのまま読み込める**（追加項目は空として扱う）。

```jsonc
{
  "schema_version": "1.1",
  // …（1.0 の項目はそのまま）…

  // 実行のたびに指定する値（例：対象月）。毎月変わる期待値を、作業手順を書き換えずに使うため
  "run_parameters": [
    { "param_id": "target_month", "label": "対象月", "type": "month", "required": true }
  ],

  "completion_criteria": {
    "version": 3,                       // 完了基準を変えるたびに +1（作業手順の版数とは別）
    "items": [
      {
        "criterion_id": "c1",           // 参照名。作業手順の中で一意
        "name": "集計前後の売上金額が一致する",
        "kind": "total_match",          // 種類（§4）
        "target": { "ref": "r2", "column": "売上金額" },          // 確かめる対象（どのステップの結果・どの列）
        "params": { "compare_ref": "r3", "compare_column": "売上金額", "tolerance": "0" },
        "on_fail": "critical",          // 満たさないとき：critical（重大）／caution（注意）／record（記録のみ。判定に使わない）
        "origin": "template",           // template／manual／ai
        "confirmation_status": "confirmed",   // ai の提案は ai_proposed。確認するまで評価に使わない
        "note": "集計の前後で金額が変わっていないことを確かめる"
      }
    ],
    // 変更の記録（何を、いつ変えたか）。値の中身ではなく、変更の要約だけを残す
    "changelog": [
      { "version": 3, "changed_at": "2026-12-01T09:00:00+09:00", "summary": "「未照合の商品コードが0件」の許容件数を 0 → 3 に変更" }
    ]
  }
}
```

**設計の判断**

| 判断 | 理由 |
|---|---|
| 完了基準を `nodes` の中に入れず、別の欄にする | 処理手順と完了基準を混同しないため（指示書 §5.1）。処理ステップを差し替えても基準は残り、どの基準がどのステップの結果を見ているかは `target.ref` で分かる |
| 期待値は値そのもの、または「実行時に指定する値」（`{"$param": "target_month"}`）を書ける | 対象期間や正解値は毎月変わる。値を書き換えるたびに作業手順を編集させないため |
| 完了基準に独自の版数と変更の記録を持つ | 「先月から基準を変えたか」を追跡できるようにするため（指示書 §10 再利用） |
| 既存の `validation_rules`（結合で行の増加を認めるか、金額の許容差）は残す | 「標準の確認」の調整値として使う。完了基準とは役割が違う |
| 種類（`kind`）は決まった一覧から選ぶ。自由な式は書かせない | プログラムで確実に判定するため。AIや利用者が任意のコードを書ける余地を作らない |

## 4. 完了基準の種類（最初に作る範囲）

| `kind` | 画面の名前 | 対象 | 設定 | 判定の根拠として表示する値 | 再利用する既存の処理 |
|---|---|---|---|---|---|
| `required_columns` | 必要な列がそろっている | 入力 | 列（入力の定義の「必ずある列」） | 足りない列 | 読み込み時の列の確認（実装済み） |
| `data_type` | データの形式に合っている | 入力・列 | 形式 | 変換できない件数・行番号の例 | `convert_value`（1-2 の形式の確認と同じ） |
| `no_blank` | 空欄がない | 結果・列 | 許容件数 | 空欄の件数・行番号の例 | 空欄の確認（missing の detect） |
| `unique` | 重複がない | 結果・列（複数可） | — | 重複したキー・件数・行番号の例 | 重複の確認（duplicates の detect） |
| `value_range` | 値が範囲内にある | 結果・列 | 最小・最大 | 範囲外の件数・例 | 条件で残す処理の比較（filter） |
| `period` | 対象期間内の日付だけ | 結果・日付列 | 開始・終了（実行時に指定可） | 期間外の件数・最も早い日・最も遅い日 | 同上 |
| `total_match` | 2つの結果で合計が一致する | 結果・列 ×2 | 許容差 | 前・後・差額 | Decimal の計算（numeric） |
| `row_count` | 件数が範囲内にある | 結果 | 最小・最大、または入力件数との比 | 件数・範囲 | 各ステップの件数（実行記録） |
| `all_matched` | 照合できない行が上限以下 | 結合ステップ | 許容件数 | 照合できない件数・キーの例・原因の候補 | 結合の照合結果（実装済み） |
| `expected_value` | 確認用の値と一致する | 結果・列の合計または件数 | 値（実行時に指定可）・許容差 | 計算値・確認用の値・差 | numeric |
| `list_rows` | 条件に合う行を一覧にする | 結果 | 条件 | 該当件数と一覧（**判定には使わない**） | filter |

**後で追加する種類**：`compare_previous`（前回の実行と比べる。中優先度）。

### 4.1 指示書の例との対応

| 例 | 完了基準 → 種類 |
|---|---|
| ①売上集計 | 必須列 → `required_columns` ／ 対象期間外なし → `period` ／ 想定外の重複なし → 標準の確認（結合の関係判定）＋ `unique`（マスタのキー）／ 集計前後の合計一致 → `total_match`（標準の確認でも行う）／ 未照合0件 → `all_matched`（許容0件） |
| ②在庫照合 | コードの対応 → `all_matched` ／ 重複キーなし → `unique` ／ 差異が許容範囲 → `value_range`（差異の列）／ 範囲外の差異の一覧 → `list_rows`。**差異を見つけること自体が目的のときは、差異の基準を「記録のみ（record）」にして、差異があるだけで失敗にしない** |
| ③移行データ整備 | 必須項目の欠損なし → `no_blank` ／ 形式の一致 → `data_type` ／ 主キー重複なし → `unique` ／ 件数が想定範囲 → `row_count`（入力件数との比）／ 対象外データの記録 → `list_rows` |

## 5. 評価（実行時）

1. 作業手順を実行する（既存の処理エンジン。各ステップの結果は実行の間メモリにある）。
2. 実行の直後に、各完了基準を**プログラムで**評価する（新しい `app/criteria/evaluate.py`）。AIは使わない。
3. 各基準の結果は次のどれか。

| 結果 | 意味 | 例 |
|---|---|---|
| 満たしている | 条件を満たした | 差額 0円 |
| 満たしていない | 条件を満たさない（重さは `on_fail` による） | 未照合 12件（許容 0件） |
| **未検証** | **確かめられなかった**。満たしているとはみなさない | 途中のステップで止まり対象の結果がない／対象の列がない／実行時に指定する値が未入力／AIの提案が未確認 |
| 対象外 | その実行では確かめる意味がない | 前回の実行がない初回の比較（`compare_previous`）。理由を表示し、判定には影響しない |

4. 根拠として、計算に使った値を必ず残す（例：集計前 12,345,678円／集計後 12,345,678円／差額 0円）。

**実装の補足（2-2）**

| 項目 | 内容 |
|---|---|
| 結果の値 | `passed`（満たしている）／`failed`（満たしていない）／`unverified`（未検証）／`not_applicable`（対象外）／`recorded`（記録：一覧にするだけの基準） |
| 評価する時 | 本番の実行の最後（途中で止まっても評価し、確かめられない基準は未検証）。プレビューでは評価しない |
| 入力の基準 | 「必要な列」「データの形式」は、読み込みステップの記録（必要な列がない・変換できない値）から判定する。任意の列がなく空欄で補った列は「ない」と数える |
| 例の行番号 | 「Excelの行」（元のファイル上。見出しの行を含む）と「結果の行」（確かめた表の、見出しを除いた何行目か）を名前で区別する |
| 実行時に指定する値 | `POST /api/runs` の `run_parameters`。未入力・形の誤りは、その値を使う基準だけを未検証にする |
| 共用した既存の処理 | 重複の数え方（`find_duplicates`、重複の確認ステップと共用）、条件の判定（条件で残すステップの関数）、空欄の判定（`is_missing`） |

## 6. 総合判定と出力の制御

**判定の規則**（上から順に当てはめる。AIは関与しない）

| 総合判定 | 条件 | 出力 |
|---|---|---|
| 重大 | 処理がエラーで止まった、または `on_fail=critical` の基準を満たしていない | **確定した結果は出力しない**。原因を調べるための検証レポート（照合できなかった行の一覧などを含む。「確定前・調査用」と明記）は出力できる |
| 未検証 | 重大はないが、`record` 以外の基準に未検証がある | 確かめられなかった項目を表示し、利用者が確認したうえで出力できる（「正常」とは表示しない） |
| 注意 | 上のどれでもなく、標準の確認の警告、または `on_fail=caution` の基準を満たしていない | 確認が必要なことを表示し、利用者が確認したうえで出力できる |
| 正常 | 上のどれでもない | 出力できる。業務の完了基準がないときは §2 の表示にする |

**判定根拠の表示**（例）

> **完了基準：未照合の商品コードが0件であること**
> 未照合件数：12件 ／ 許容件数：0件 ／ 判定：重大
> 対応：商品マスタを確認してください（照合できなかったコードの例：P-1099、P-2001）

出力する Excel にも、総合判定・各基準の結果と根拠・確認した日時を「検証結果」シートとして含める（タスク 1-7・2-5）。

## 8. 既存の実装をどこまで再利用できるか

| 既存の部品 | 再利用 | 補足 |
|---|---|---|
| 処理エンジン（15種・結合と集計の検証） | **そのまま** | 「標準の確認」になる。変更は不要 |
| `EngineIssue`（問題の記録：何が・原因・直し方・例） | **そのまま** | 標準の確認の結果を総合判定に集約する元データ |
| 実行の中の各ステップの結果（`Execution.tables`） | **そのまま** | 完了基準の評価の対象。追加の実行は不要 |
| 型の変換・比較・空欄・重複の判定の関数 | **関数として切り出して共用** | 現在は各処理ステップの中にある。評価からも呼べるように、小さく切り出す（動作は変えない） |
| `RunResult.can_export`（エラーなら出力不可） | **置き換え** | 総合判定にもとづく出力の制御に変える |
| 作業手順の形の検証（1.0） | **拡張** | 1.1 を追加し、1.0 は自動で 1.1 として読む |
| 画面：処理ステップの一覧（1-3） | **そのまま** | 完了基準は別の欄（「何を満たせば完了？」）として並べる |

## 9. 操作の流れ（単発業務と定型業務）

処理エンジンと確認の仕組みは1つ。違うのは導線だけ。

| 段階 | A. 今回だけの作業 | B-1. 繰り返し使う作業を作る | B-2. 保存した作業を回す（Phase 4） |
|---|---|---|---|
| 始め方 | ファイルを読み込む | ファイルを読み込む（A と同じ） | 保存した作業手順を選ぶ → 新しいファイルを指定 |
| 1 何をする？ | AIの提案または手動で作る | 同左 | 編集しない |
| 2 何を満たせば完了？ | 標準の確認のみでも可。必要なら基準を追加 | 基準を設定（実行のたびに指定する値も） | 実行のたびに指定する値（対象月など）だけ入力 |
| 3 実行して確かめる | 総合判定と判定の理由 | 同左 | 同左 ＋ 入力の変化の検出（Phase 3）、前回との比較（Phase 6） |
| 4 出力 | 結果と検証レポート。**保存は任意** | 同左 ＋ 作業手順と完了基準を保存 | 結果と検証レポート |
| 前回との比較 | 行わない | 初回は対象外 | 設定していれば行う |

**単発から定型へ**：A の途中・実行後・出力後のどこでも「この作業手順を保存する」を選べる。保存すると B-1 で作ったものと同じになる（作り直しは不要）。実行済みなら、その実行の要約を「前回の実行」として一緒に残す。

**段階表示（画面上部）の変更案**

| 現在 | 変更後 |
|---|---|
| 1 データを読み込む | 1 データを読み込む |
| 2 作業を伝える | 2 何をする？（AIに伝える・手動で作る） |
| 3 作業手順を確認する | 3 何を満たせば完了？ |
| 4 作業を実行する | 4 実行して確かめる |
| 5 出力・保存する | 5 出力する（保存は任意） |
