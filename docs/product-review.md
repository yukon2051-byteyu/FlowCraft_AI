- 版：v1.0（2026-11-12）
- 位置付け：製品方針 再定義・開発計画改訂指示書 Ver.3.0 にもとづく、製品の存在意義と設計判断の記録
- 経緯：開発者（筆者）が ChatGPT と議論した論点に対し、Claude Code が独立したレビューを行い、その提案を ChatGPT と再検討したうえで、筆者が方針を決定した

## 1. 開発の背景

FlowCraft AI は、Excel・CSV を使った定型業務（月次売上集計、マスタとの照合、在庫差異の確認など）を、業務ごとに専用のプログラムを作らずに自動化する Web アプリとして開発を始めた。

開発の途中で、次の根本的な疑問が生じた。

> 今は誰でも生成AIで Python や VBA を作れる。Claude Code を使えば業務専用のアプリも作れる。それでも FlowCraft AI を使う理由はあるのか。

この問いに答えるため、製品の存在意義・対象ユーザー・優先順位を見直した。

## 2. 解決したい業務課題

自動化を「作る」ことは、生成AIによって大幅に容易になった。現場で残っている課題は、作った後の**運用**にある。

| 課題 | 現場で起きること |
|---|---|
| 入力データの変化 | 翌月、列名が「売上金額」から「金額」に変わり、スクリプトが止まる。または、止まらずに誤った数字を出す |
| 誤集計に気づけない | マスタに同じ商品コードが2行あり、売上が2倍で集計される（ExcelのVLOOKUPやスクリプトの結合で起きやすい）。エラーにならないため誰も気づかない |
| 入力の取り違え | 先月のファイルを選んだ、一部の支店のファイルが抜けている。処理自体は正しく動くため気づけない |
| 担当者への依存 | 作った人しか直せない。異動・休暇で回せなくなる |
| 統制 | 情報システム部門は、AIが書いたスクリプトやマクロを1本ずつ審査できない |

## 3. 生成AIによる個別開発との違い

| 観点 | 生成AIで個別に開発 | FlowCraft AI |
|---|---|---|
| 作る速さ | 速い（特に、作る人がプログラムを読める場合） | 同程度（AIが作業手順を提案） |
| 自由度 | 高い | 標準の処理ステップの範囲に限られる |
| 検証 | **頼まなければ付かない**（初心者は頼むことを知らない） | 結合・集計の検証が**最初から必ず付く** |
| 入力の変化への対応 | 止まるか、黙って誤った結果を出す | 実行前に列構成の変化を検出し、利用者に確認する |
| 引き継ぎ | コードを読める人が必要 | 処理内容を業務の言葉で表示。回す人は手順を選んで実行するだけ |
| 統制 | スクリプトごとに審査が必要 | 許可された処理しか動かない仕組みを一度審査すればよい |

**結論**：自分で作って自分で使う人にとっては、生成AIによる個別開発のほうが合理的な場合が多い。FlowCraft AI が価値を持つのは、**作る人と回す人が違う、入力が毎月変わる、組織として統制が必要**という条件がそろうときである。

なお、「業務ごとにプログラムが増える」ことは、現場の担当者にとっての痛みとしては弱いと判断した。担当者が気にするのは本数ではなく「来月も動くか」「数字は合っているか」「担当が休んだら誰が回すか」である。訴求の軸はこちらに置く。

## 4. 既存製品との比較

**注意**：以下の他社製品の機能は、筆者側の知識にもとづくもので、最新の状況を一次情報で確認したものではない。

| 製品 | 特徴（未確認を含む） | FlowCraft AI との関係 |
|---|---|---|
| Power Query | Excel に標準で付属。手順の記録・再実行ができる。一般の担当者にとって最大の競合 | 変換の機能では勝負しない。結合で行が重複しても標準では警告されない、列名が変わったときのエラーが分かりにくい、といった点（理解ベース）を補う立場をとる |
| Alteryx・KNIME | 処理部品・接続先が非常に多い分析者向け製品。AI支援機能を持つ | 機能の広さでは勝負しない |
| Parabola | 業務チーム向けのワークフロー製品。AI機能あり。英語圏中心 | 同上 |

**面接での想定問答**

> Q. Power Query ではだめなのですか？
> A. Power Query は変換を記録・再実行する優れた道具です。FlowCraft AI が提供するのは、その結果が正しいかを毎回確かめ、入力の変化に気づき、誰が回しても事故が起きない運用です。結合時の重複検出や金額の照合を標準で行うため、処理エンジンを自前で持つ設計にしました。

## 5. FlowCraft AI の差別化

製品コンセプト：**「AIで作る。人が確かめる。毎月、正確に回す。」**

差別化の中心は、後半の2つ（確かめる・回す）にある。「AIで作る」は生成AIと同じ土俵であり、それだけでは差別化にならない。

最も重要な提供価値：

1. 毎月の作業を安全に繰り返せる
2. 入力データや処理結果の異常に気づける
3. 担当者が変わっても作業を引き継げる

「正確に回す」は、結果の正確性を無条件に保証する意味ではない。**検証できる範囲と限界を利用者に示す**ことを前提とする（例：前回との件数の違いは「確認が必要」と示すだけで、誤りとは断定しない）。

## 6. ターゲットユーザー

| 役割 | 主な対象 | 求めるもの |
|---|---|---|
| **作る人** | 社内SE、DX推進担当、Excelに詳しい現場リーダー、業務改善担当 | AIの支援で早く作る。検証結果で正しく作れたと確かめる |
| **回す人** | 一般事務、営業事務、経理、製造現場の管理担当 | 手順を選び、ファイルを指定して実行するだけ。問題があれば何をすればよいか分かる |

**採用しなかった案**：一般事務の担当者に、作業手順をゼロから作ることまで求める案。画面が複雑になるうえ、そこは生成AIが最も得意で差がつかない部分だからである。

## 7. 作る人／回す人の役割分担

- 画面を「作る画面」と「回す画面」に分ける
- 回す画面では、処理ステップの編集や技術的な設定を求めない
- MVP では利用者管理・権限管理は作らない（画面と操作の流れを分けることを優先）。正式な承認や権限は将来の拡張とする

## 8. 品質保証の設計思想

### 8.1 二つの層

| 層 | 確かめること | 例 | 状況 |
|---|---|---|---|
| 処理の正しさ（1回の実行の中） | 処理そのものが正しく動いたか | 結合前に関係（1対1・多対1など）を判定し想定と違えば停止、結合後の行数＝予測、結合前後の金額の照合、集計前後の合計の照合 | 実装済み |
| 入力の正しさ（実行と実行の間） | そもそも正しいデータを入れたか | 前回の実行との比較、対象期間、確認用の正解値との照合、業務ルール | Ver.3.0 で追加 |

1回の実行の中の検証だけでは、ファイルの取り違えや支店の抜けは見つけられない。処理は正しく動くからである。これが二つ目の層を追加した理由である。

### 8.2 重大度による結果の扱い

| 判定 | 意味 | 結果の扱い |
|---|---|---|
| 正常 | 検証上の問題がない | 確定・出力してよい |
| 注意 | 確認が必要な変化がある（前回から件数が大きく変動、未使用の列の追加、新しい商品コードの出現など） | 内容を表示し、利用者の確認後に出力できる |
| 重大 | 結果の信頼性に大きく影響する（必須列の欠落、結合での想定外の重複、正解値との不一致など） | 確定した結果としては出力しない。原因を調べるための検証結果・エラーレポートは出力できる |

前回との変動率だけで「重大」とは判定しない。季節変動や業務の変化があるため、利用者が設定した許容範囲と、検証ルールの性質で判定する。AIの推測だけで重大度を決めることもしない。

### 8.3 データを黙って変えない

これまでの開発で一貫させてきた原則。空欄を0とみなさない、先頭0のコードを数値にしない、全角数字を勝手に変換しない、照合できなかった行を削除しない、など。

## 9. React Flow を MVP で採用しない理由

当初の仕様では、React Flow（ノードを線でつなぐ図）による編集画面を予定していた。

**採用しない理由**
- FlowCraft AI の処理は「上から順に実行する」構造であり、線でつなぐ図にしなくても表現できる
- 一般の利用者には、縦の一覧のほうが理解しやすい
- 画面が複雑にならず、開発・保守の負担も抑えられる

**複数の入力を扱う場合の確認**：処理エンジンは、各ステップが「どのデータを使い、どのデータを作るか」を名前で持つ。さらに「使えるのは、自分より上で作られたデータだけ」という決まりで検証している（作業手順の形の決まり R1）。このため、縦の一覧の中で「使うデータ：ステップ2の結果、商品マスタ」と表示すれば、結合（2つの入力）や、同じデータから2つの集計を作る枝分かれも、正しく表現できる。

**将来**：条件分岐や並列の処理が必要になった場合は、ノードを線でつなぐ図の採用を再検討する。内部の形式（ステップどうしのつながりの情報）はすでに持っているため、表示を追加するだけで対応できる。

## 10. 分析機能の優先度を下げた理由

- 分析・グラフは、BIツールや Excel のピボット・グラフで十分に代替できる領域であり、差別化の中心ではない
- 製品の中心である「継続運用と品質保証」が完成する前に分析を広げると、数字が正しいと言えないまま分析だけが増える

MVP では、前月比・ランキング・構成比、棒グラフ・折れ線グラフに絞り、継続運用と品質保証の後に実装する。高度な統計、分析専用のダッシュボード、多数のグラフ形式、AI分析コメントは後回しにする。

## 11. 別業務への AI 適応を後回しにした理由

- 業務の違いが大きい場合（変更が手順の半分以上、元の手順が単純）は、新しく作るほうが簡単である
- より頻繁に起きるのは「部署をまたいだ流用」ではなく「同じ業務の、毎月の入力の変化」である
- 再利用に価値があるのは、手順の大半が同じで、元の手順に検証済みの業務ルール（返品の除外、端数処理、照合方法など）が詰まっている場合である

まずは「複製＋列構成の比較＋手動の修正」を作り、AIによる変更提案は第2段階とする。

## 12. 今後の開発計画（要約）

詳細は [implementation-plan.md](implementation-plan.md)。

| フェーズ | 内容 | 優先度 |
|---|---|---|
| Phase 0 | 基盤・処理エンジン・検証（**完了**） | — |
| Phase 1 | 作業手順の作成・保存・読み込み・再実行・Excel出力 | 最優先 |
| Phase 2 | 再実行時の列構成の確認、既存の品質検証を画面に接続 | 最優先 |
| Phase 3 | 前回との比較、対象期間、異常時の出力制御、検証レポート | 高 |
| Phase 4 | 作る画面／回す画面の分離 | 高 |
| Phase 5 | AIによる作業手順の作成、AI利用の認証 | 高 |
| Phase 6 | 基本の分析・グラフ | 中 |
| Phase 7 | 別業務への応用 | 中〜低 |

## 13. 制約・未解決の課題

| 課題 | 内容 |
|---|---|
| 実利用者による検証がない | 作る人・回す人それぞれ数名に、架空データで使ってもらい、迷った点・所要時間を記録する必要がある |
| 効果の数値がない | 作業時間の削減などは、想定値と実測値を区別して示す必要がある |
| 運用設計 | 誰が手順を作り、誰が確認し、問題が起きたら誰が直すか。MVP では画面の分離までにとどめ、承認・権限は将来の課題 |
| 処理の表現力 | 標準の処理ステップで表現できない業務には対応できない。対応範囲を利用者に明示する必要がある |
| 他社製品の機能 | 本書の比較は一次情報で未確認。面接で使う前に、公式情報で確認する |
| 公開環境での保存 | サーバーにデータを残さない方針のため、作業手順と実行記録はブラウザ内とファイルに保存する。ブラウザのデータが消えると一覧も消える |
