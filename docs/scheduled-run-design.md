# 無人定期実行 設計書（scheduled-run-design.md）

- 版：v0.1（2026-11-13 設計のみ。実装は未着手）
- 元の指示：無人定期実行機能 開発指示書（改訂完全版）＋ 共通Worker方式 開発指示書（2026-11-13）
- 2つの指示書で食い違う部分は、**後の指示書（共通Worker方式・Windowsタスクスケジューラ）を正式とする**（§1）
- 対象はPCのブラウザ（Windows 11・Chrome／Edge・1366×768〜1920×1080）。スマートフォン向けの画面は作らない

---

## 0. 結論（この設計で決めること）

1. **無人実行は「設定しただけでは動かない」**。設定保存 → 接続テスト → テスト実行 → 品質検証 → 利用者による明示的な有効化、の5段階を通った案件（ジョブ）だけを、Worker が実行する
2. **確認の結果は「設定の版」に結び付ける**。処理に影響する設定を変えたら、以前の確認結果は使わず「要再検証」に戻す
3. 構成は **Web（FastAPI）＋ 共通Worker（Python）＋ 共有データベース（SQLite）＋ Windowsタスクスケジューラ（5分ごとに Worker を1つ起動）**。最初は1台のWindows端末で動かす
4. **二重実行はデータベースで防ぐ**（「案件＋実行予定日時」の一意制約と、実行権の期限付き確保）。メモリ上の印やローカルの目印ファイルには頼らない
5. **正式なファイルは、品質検証を通ってから確定する**（一時ファイルに書き、確認後に名前を変えて確定。既存の正常ファイルは上書きしない）
6. 処理は既存のエンジン（`app/engine`）と Excel 出力（`app/export`）をそのまま使う。Worker 専用の加工処理は作らない
7. 実装は **作業手順の保存（1-8〜1-11）・完了基準（Phase 2）・入力の変化の検出（Phase 3）の後**（§13）。品質検証の「正常／注意／重大／未検証」は Phase 2 で作るため

## 1. 2つの指示書の食い違いと、採用する方針

| 項目 | 1件目（改訂完全版） | 2件目（共通Worker方式） | 採用 |
|---|---|---|---|
| 起動のしくみ | 外部スケジューラ（GitHub Actions など）でもよい | Windowsタスクスケジューラが共通Workerを5分ごとに起動 | **2件目** |
| 実行する場所 | Hugging Face Spaces 前提で検討 | 社内ネットワークにつながったWindows端末 | **2件目**。Spaces は社内のフォルダに届かないため |
| 最初の入出力 | 実際に接続できる方式 | ローカルフォルダ・検証用フォルダ | **ローカルフォルダ** |
| 二重実行の防止 | Phase 3 | Phase 1 | **Phase 1**（安全の土台のため） |
| データベース | 永続ストレージ | PostgreSQL などを候補 | **最初は SQLite、後で PostgreSQL に移せる作り**（§5） |

**公開版（Hugging Face Spaces）での扱い**：公開版では Worker が動かないため、無人定期実行の画面は「ローカル版でのみ利用できます」と表示する。動かない機能を、使えるように見せない。

## 2. 構成

```text
 ┌──────────── 1台のWindows端末（Phase S1） ────────────┐
 │                                                       │
 │  FlowCraft AI Web（FastAPI＋画面）                     │
 │   ・案件の設定・接続テスト・テスト実行・品質検証の確認    │
 │   ・有効化・一時停止・実行履歴・Workerの稼働状態         │
 │          │ 読み書き                                     │
 │          ▼                                              │
 │  共有データベース（SQLite：flowcraft.db）                │
 │   案件・設定の版・確認結果・実行予定・実行履歴・操作履歴  │
 │          ▲ 読み書き（トランザクション）                  │
 │          │                                              │
 │  FlowCraft Worker（python -m app.worker → 後で exe）     │
 │   ・実行対象の判定 → 実行権の確保 → 取得 → 処理          │
 │     → 品質検証 → 確定 → 履歴 → 通知                      │
 │          ▲ 5分ごとに起動（同時起動はしない設定）         │
 │  Windowsタスクスケジューラ（タスクは1つだけ）            │
 │                                                       │
 │  参照先フォルダ（例 D:\共有\売上）／出力先フォルダ       │
 └───────────────────────────────────────────────────────┘
```

- **Phase S1 では、Web と Worker は同じ端末で、同じデータベースのファイルを使う**。Worker は Web を HTTP で呼ばず、エンジンとデータベースを直接使う。Worker 用の通信の認証（指示書 §18）は、Web と Worker を別の端末に分ける段階（S3 以降）で作る
- 将来、Worker を複数の拠点で動かすときは、案件ごとに「実行できる Worker」を紐付ける（指示書の補足）。S1 の表にも `worker_group` の列だけは用意し、値は1種類で使う

## 3. 案件（ジョブ）の状態

ジョブの状態と、1回ごとの実行結果は**別々に**持つ（例：ジョブは「有効」でも、11月分の実行結果は「注意」）。

| 状態 | 意味 | Worker が定期実行するか | 主な移り先 |
|---|---|---|---|
| 下書き | 設定の途中。新しく作った案件は必ずここから | しない | 検証待ち（必須の設定がそろって保存） |
| 検証待ち | 設定は保存済み。確認がまだ終わっていない | しない | 有効化可能（3つの確認がすべて合格） |
| 有効化可能 | 接続テスト・テスト実行・品質検証が、**今の設定の版で**合格 | しない | 有効（利用者が最終確認画面で有効化） |
| 有効 | 利用者が明示的に有効化した | **する** | 一時停止／要再検証／エラー停止 |
| 一時停止 | 利用者が止めている | しない | 有効（再開時に、設定・確認結果がまだ有効かを確かめる） |
| 要再検証 | 処理に影響する設定を変えた | しない | 検証待ち → 有効化可能 → 有効 |
| エラー停止 | 重大な問題で自動的に止めた（例：3回続けて失敗） | しない | 原因を直して再検証 |

- **状態を変えるのはバックエンドだけ**。画面はボタンの表示を変えるだけで、実行してよいかは判断しない
- Worker は、実行の直前にも「有効か」「確認済みの版と今の版が同じか」を**もう一度**確かめる（画面・バックエンド・Worker の3か所で確認）
- 状態の変更と、誰がいつ何をしたかは「操作履歴」に残す

## 4. 設定の版と再検証（今回もっとも重視する点）

設定を保存するたびに「設定の版」（1, 2, 3 …）を上げる。確認結果（接続テスト・テスト実行・品質検証）は、**その時の設定の版と、設定内容の指紋（ハッシュ）**に結び付けて保存する。

| 変えた設定 | 扱い |
|---|---|
| 参照先・対象ファイルの選び方・作業手順（版）・完了基準・出力先・出力形式・接続の認証 | **要再検証**。以前の合格は使わない |
| スケジュール（日時・繰り返し） | 再検証はしない。ただし次回の実行予定を計算し直して表示し、**利用者が承認してから適用**する |
| 案件名・通知先・通知の条件・メモ | 再検証しない（処理の結果に影響しないため） |

- 作業手順は、案件に登録した時点の内容を**そのまま固定して**保存する（作業手順の ID と版、内容の指紋）。元の作業手順を編集しても、案件の中身は勝手に変わらない。画面には「新しい版があります」と示し、切り替えるときは要再検証にする
- 有効化できるのは「**確認結果の指紋 ＝ 今の設定の指紋**」のときだけ

**例**：毎月正常に動いていた「月次売上集計」で、参照先を `D:\共有\売上` から `D:\共有\売上_新` に変えた → 設定の版が 4 → 5 に上がる → 版 4 の合格は使えない → 「要再検証」になり、Worker は実行しない。

## 5. データベース

**SQLite を選ぶ理由**：Python に最初から入っていて、追加のサーバーが要らない。トランザクションと一意制約が使え、同じ端末の複数のプロセス（Web と Worker）から安全に使える。初心者でも保守しやすい。
**PostgreSQL に移すとき**：Web と Worker を別の端末に分けるとき（S3 以降）。SQL は両方で動く書き方に限定し、データベースを扱う処理を1か所（`app/jobs/db.py`）にまとめておく。

| 表 | 主な列 |
|---|---|
| jobs | job_id、案件名、状態、現在の設定の版、確認済みの設定の版、次回実行予定（UTC）、タイムゾーン、worker_group、最終実行日時・結果、作成・更新日時 |
| job_versions | job_id、設定の版、設定の内容（JSON：参照先・ファイルの選び方・作業手順の固定内容・出力先・形式・スケジュール・通知・注意時の扱い）、指紋、保存した人・日時 |
| job_checks | job_id、設定の版、種類（接続／テスト実行／品質検証）、結果、詳細、確認日時 |
| job_runs | run_id、job_id、**実行予定日時（＝重複防止の鍵）**、対象期間、状態（確保済み／実行中／正常／注意／失敗／中断／実行漏れ）、実行権の期限、最後の生存報告、開始・終了、入力ファイル（名前・更新日時・指紋）、作業手順の版、件数、品質検証の結果、出力先、エラー、再試行回数。**一意制約：(job_id, 実行予定日時)** |
| notifications | run_id、通知の手段、送信結果、エラー、日時（**実行結果とは別に記録**） |
| workers | worker_id、端末名、最終起動・最終終了・最終の正常な処理の日時 |
| audit_log | 誰が・いつ・どの案件に・何をしたか（設定変更・有効化・一時停止など） |

- 日時は UTC で保存し、画面では日本時間（Asia/Tokyo）で表示する
- **パスワードなどの認証情報は、このデータベースにも JSON にも平文で保存しない**。ローカルフォルダは Worker を動かす Windows アカウントの権限で読むため、S1 では認証情報を持たない。クラウド（S2）では Windows の資格情報マネージャーを使う
- データベースのファイルは、アプリの作業フォルダ（Git の管理外）に置く。`.gitignore` に入れる

## 6. Worker の処理

```text
python -m app.worker            ← 通常（タスクスケジューラから）
python -m app.worker --job <ID> ← 保守・検証用（定期実行では使わない）
```

1. 起動を記録（workers 表）
2. **期限切れの実行権を回収**：「実行中」のまま実行権の期限が切れたもの（前の Worker が途中で止まった）を「中断」にして記録する
3. **実行対象を探す**：状態が「有効」、次回実行予定 ≦ 今、確認済みの版 ＝ 今の版、worker_group が一致
4. **実行権の確保**（1件ずつ、トランザクションの中で）：job_runs に (job_id, 実行予定日時) を書き込む。**一意制約により、同じ予定を2つ目の Worker が書き込もうとすると失敗する** → その案件は飛ばす。書き込めたら、次回実行予定を次の日時に進める
5. 確保した後、**もう一度**状態と設定の版を確かめる（確保の直前に一時停止された場合などに備える）
6. 対象ファイルを選ぶ（§8）→ 読み込み → 入力の検証（Phase 3 の列構成の比較）
7. 固定した作業手順を、既存のエンジンで実行
8. 品質検証（Phase 2 の完了基準）→ 総合判定
9. 判定に応じて出力（§9）
10. 実行履歴を記録 → 通知（通知の失敗は別に記録）
11. 実行中は1分ごとに生存報告を書き、実行権の期限を延ばす。終了で実行権を手放す

- 複数の案件が同時に対象になったら、**実行予定の早い順に1件ずつ**処理する（S1）。1件の失敗が他の案件を止めないようにする
- 実行の途中で次の Worker が起動しても、すでに確保された予定は飛ばすため二重にならない。タスクスケジューラ側でも「すでに実行中なら新しく起動しない」設定にする（二重の対策）

### 実行漏れ（PCが止まっていた場合など）

| 案件ごとの設定 | 初期値 |
|---|---|
| 遅れの許容時間 | 60分 |
| 許容時間を過ぎた予定 | **実行せず「実行漏れ（確認待ち）」として記録し、通知する**。利用者が画面で「この回を実行する」を選んだときだけ実行 |
| 過去分を自動で補う | しない（する場合も最大1件） |

10日間PCが止まっていた「毎日」の案件でも、復帰時に10回分をまとめて実行することはない。

## 7. スケジュール

- 種類：毎日／毎週（曜日）／毎月（日付または「月末」）／指定日時（1回だけ）。「ファイルが届いたら実行」は将来の検討
- 基準は日本時間。タイムゾーンを設定として保存する
- **存在しない日付**（例：毎月31日 → 11月）：その月の最終日に実行する（画面に明記）
- **休日**：S1 では扱わない（「土日・祝日なら前後の営業日」は S3 で検討。祝日の一覧が必要なため）
- 画面には次回の実行予定と、**「5分ごとの確認のため、実行開始は予定から最大5分ほど遅れることがあります。PCの電源が切れていると実行されません」**と表示する（精度を言い過ぎない）

## 8. 対象ファイルの選び方

- 設定：対象フォルダ、ファイル名のパターン（例 `sales_{YYYYMM}.xlsx`）、対象期間の決め方（例：実行日の前月）、ファイル形式
- 例：12月1日の実行 → 対象期間 2026年11月 → `sales_202611.xlsx` を探す
- 次のときは**勝手に選ばず止める**：見つからない／候補が2つ以上ある／ファイル名の年月と対象期間が合わない／形式が違う／壊れている／読めない（権限がない）
- 見つからないときは「未着」として記録し、設定に応じて次の起動時に再確認する（S3。S1 は止めて通知）

## 9. 出力と、既存ファイルの保護

1. 出力先のフォルダに、一時ファイル（`~flowcraft_<run_id>.tmp`）として書く
2. 品質検証の総合判定を見る
   - **正常**：一時ファイルの名前を正式な名前（例 `月次売上集計_202611.xlsx`）に変えて確定する
   - **注意**：案件ごとの「注意のときの扱い」に従う（初期値：**正式には出力せず、確認待ちにする**。事前に「この注意は出力してよい」と承認していれば確定する）
   - **重大・未検証**：正式には出力しない。確認結果（調査用）だけを検証用フォルダに残す
3. 同じ名前の正式ファイルがすでにあるときは、**初期値では上書きしない**（止めて通知）。再実行で上書きしたいときは、利用者がその回について明示的に許可する
4. 失敗したら一時ファイルを消す。消せなかった一時ファイルは、名前で正式なファイルと区別できる
5. 同じ実行の再試行は同じ run_id を使うため、成果物が二重にできない

## 10. 5段階の確認の中身

| 段階 | 確認すること | 合格の条件 |
|---|---|---|
| 1 設定保存 | 必須の設定がそろっている（作業手順・参照先・ファイルの選び方・スケジュール・出力先） | そろっていれば「検証待ち」 |
| 2 接続テスト | 参照先：フォルダがある・一覧が取れる・対象ファイルを読める。出力先：フォルダがある・**テスト用のファイルを作って消せる**（既存のファイルには触れない） | すべて成功 |
| 3 テスト実行 | 参照先から実際にファイルを選び（または利用者が指定したテストデータで）、作業手順を実行し、出力ファイルを作る。**出力は検証用フォルダにだけ書く**（本番の出力先には書かない）。件数・処理時間を記録 | 最後まで実行できた |
| 4 品質検証 | テスト実行の結果を、完了基準で判定（正常・注意・重大・未検証） | 重大がない、かつ重要な項目に未検証がない。注意は、その内容を承認した場合のみ |
| 5 有効化 | 最終確認画面（案件名・参照先・対象ファイル・作業手順・スケジュール・次回実行予定・出力先・通知先・テスト実行と品質検証の結果）に「有効化すると、指定した日時にファイルの取得・処理・出力が自動的に実行されます。」と表示し、利用者が確認して押す | バックエンドが「確認結果の指紋 ＝ 今の設定の指紋」を確かめてから「有効」にする |

画面では、押せないボタンには**何を終えれば押せるか**を書く（例：「接続テストがまだです」「品質検証で重大な問題が1件あります」）。

## 11. 画面（PC専用）

| 画面 | 内容 |
|---|---|
| 無人定期実行の一覧 `/jobs` | 案件名・スケジュール・状態・次回実行・最終結果・操作。上部に Worker の稼働状態（最終起動・実行待ちの件数・エラー停止の件数）。**最終起動から15分以上たっていたら警告**（止まっているのに「稼働中」と見せない） |
| 無人定期実行の設定 `/jobs/:id` | 左：設定（案件名・作業手順・参照先・対象ファイル・スケジュール・出力先・通知）。右：5段階の進み具合・各確認の結果・次回実行予定・有効化できるか。下：設定を保存／接続テスト／テスト実行／品質検証の結果を見る／無人定期実行を有効化 |
| 実行履歴 | 一覧（正常・注意・失敗・実行漏れを色と文字で区別）→ 詳細（入力ファイル・件数・判定の根拠・エラーと直し方・再実行） |

配色は既存どおり（ミント＝実行・成功、ゴールド＝注意、エラーの赤＝失敗）。コーラルは見直し（カイゼン）専用のため、ここでは使わない。

## 12. 通知

- S1：**画面の中のお知らせ**（一覧の上部に「確認が必要な実行が2件あります」）と、実行履歴への記録。外部へは送らない
- S3：メール・Microsoft Teams（Webhook）。送信の設定（宛先・Webhook の URL）は認証情報と同じく平文で保存しない
- 通知の条件：すべて／注意・失敗のときだけ（初期値）／重大のときだけ
- 通知の本文に業務データ（金額・顧客名など）を入れない。案件名・実行日時・対象期間・結果・件数・エラーの概要・履歴へのリンクだけ

## 13. 開発の順番（提案）

| 段階 | 内容 | 前提 |
|---|---|---|
| **S1** | 共通Worker の基盤：案件の登録（複数）・設定の版・5段階の確認・状態管理・Worker（判定・確保・実行・確定）・実行漏れの扱い・二重実行の防止・実行履歴・画面の中のお知らせ・ローカルフォルダの入出力・タスクスケジューラの登録スクリプトと手順書 | 1-8〜1-11（作業手順の保存・版）、Phase 2（完了基準・総合判定）、Phase 3（入力の変化の検出） |
| S2 | 外部ストレージ：OneDrive／SharePoint（Microsoft Graph）・Google Drive。認証は資格情報マネージャー | S1。利用者側でアプリの登録（Azure など）が必要 |
| S3 | 運用の強化：未着時の再確認・再試行（回数制限）・メール／Teams 通知・手動再実行・休日の扱い・Web と Worker の分離（HTTPS＋Worker専用の認証）・PostgreSQL・exe 化（PyInstaller） | S1 |
| S4 | 継続的な改善：処理時間・エラーの傾向・改善前後の比較（Phase K2・6・7 とつなげる） | S1〜S3 |

**S1 の完了条件**：1つの Worker が複数の案件から実行対象を判定し、**5段階の確認を経て有効化した案件だけ**を、指定した時刻（から5分以内）に無人で実行すること。指示書のテスト（正常系10件・異常系12件）を自動テストで確かめる。

**S1 を Phase 3 の後に置く理由**：品質検証（正常・注意・重大・未検証）は Phase 2 の完了基準そのもので、入力ファイルの取り違えや列の変化に気づく仕組みは Phase 3 で作る。これらがない状態で無人実行を作ると、「処理は終わったが結果が正しいかは分からない」ものを自動で出力することになり、この機能の安全性の根拠がなくなる。

## 14. テストの方針

- 時刻は**テストから指定できる**ようにする（Worker に「今」を渡せる作り）。実際に5分待つテストはしない
- 二重実行：同じ予定に対して、2つの Worker（別プロセス）を同時に動かし、実行が1回だけになることを確かめる
- 既存ファイルの保護：出力先に正常なファイルを置き、品質異常・途中失敗のあとも中身が変わらないことを指紋で確かめる
- 通知の失敗：通知の手段をわざと失敗させ、実行履歴が残ることを確かめる
- Windowsタスクスケジューラへの登録そのものは自動テストにしない（端末の設定を変えるため）。登録スクリプトは、実行前に内容を表示して確認をもらう

## 15. 実装しないこと・あとで検討すること

- AI を無人実行の中で呼ぶこと（S1〜S3 では呼ばない。AIの使用パスワードを保存して使い回すことはしない）
- スマートフォン向けの画面
- 案件ごとにタスクスケジューラのタスクを作る方式（採用しない）
- 休日の一覧、ファイルが届いたら実行、複数拠点の Worker の振り分け
